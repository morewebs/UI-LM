# The model

Date: 2026-10-28. The first model that reads a screen and describes it, and the numbers it
was measured at.

## What it is

A softmax regression over seventeen features read off the screen itself: a tool glyph at the
start of a row, a quantity against a limit, a border character, a key binding, the vertical
position of a row, and so on. It answers one question per row — ordinary text, a tool call, a
meter, a reasoning line — and the page builder turns those answers into components using the
same constructors the rule-based reader uses.

Size is a choice, not a compromise: ninety screens produce about three and a half thousand
rows, and a model with more parameters than examples would memorise the corpus and report a
number about itself.

## Numbers

Row level, on a held-out fifth of the corpus:

```
row accuracy — train 98.3%, held out 98.8%
  held-out Block     recall 99.0%
  held-out ToolCall  recall 66.7%
  held-out Meter     recall 100.0%
```

Page level, on sessions recorded *after* training and therefore never seen:

| | model | do-nothing floor |
|---|---|---|
| weighted structure | **79.9%** | 41.0% |
| blocks reproduced | 44 of 62 | — |
| meters reproduced | **11 of 11** | **0** |
| tool calls reproduced | 3 of 6 | 0 |

The margin over the floor is what matters. A number alone cannot distinguish a model from a
paragraph splitter; the pair of them can.

## The bug that the score found, not the tests

The first page-level score was **53.5%**, with blocks at 11 of 78. The model's row labels were
fine; the *grouping* was not. Every row labelled "text" was merged into a single block,
because the builder consulted only the label and never the screen — so a page of nine blocks
came back as one enormous one.

Splitting a run at a blank row and at a border — the reader's own separators — took the same
model, with the same weights, from 53.5% to **79.9%**. Nothing about the model changed. This
is the argument for scoring the thing rather than the parts: every unit test passed while the
model scored half of what it should.

## What it does not do

- **Tool calls are half-found** (3 of 6). The rows are recognised; what the application named
  in them is not always read the same way twice.
- **Reasoning lines were not reproduced at all** in the first measurement.
- **Ninety screens is not a corpus.** The margin is real and the model is small; neither
  substitutes for more data.

## Measured on a batch it never saw

Trained on one recording batch (91 pairs, 3,588 rows), scored on a second batch recorded afterwards — 13 sessions, 178 frames:

```
model 80.8%  floor 23.4%  over 178 frame(s), trained on 91 screen(s)
  Block      508/729 reproduced
  Meter      121/121 reproduced
  Thought     17/17  reproduced
  ToolCall    118/190 reproduced
```

The margin is 57 points, and it did not collapse when the evaluation moved from 16 frames to 178 — which is the check that matters, since a margin that shrinks with more data is a model fitting its corpus.

| component | model | floor |
|---|---|---|
| Block | 70% | — |
| Meter | **100%** | 0% |
| Thought | **100%** | 0% |
| ToolCall | 62% | 0% |

## The second bug the score found

Reasoning lines scored **0 of 17**. The reference page keeps the drawn line verbatim, and the builder only applied the reasoning rule when the model happened to label the row a tool call — with nine reasoning rows in training, it often did not. The rule now lives where the reader has always kept it: a single row that says `♦ Thought for 3.0s` is reasoning, whatever the model called it.

That took reasoning from 0 of 17 to **17 of 17** and the page score from 77.6% to **80.8%**, with the same trained weights.

## The lesson, twice in two rounds

Both times, a component scored zero or near-zero while every unit test passed, and both times the cause was in the *construction* rather than the model. A model is only as good as the assembly around it, and the page score is the only measurement that sees both.

## Why tool calls sit at 62%

A frame with three tool lines was compared component by component — the reader against the model, both through the same page builder:

```
reference   rows=11-12  [     ♦ Edited notes.txt, explored 1 directory, 1 file, 1 search +1 -1 ]
model       — the same row came back as plain text
reference   rows=13-14  [     ♦ post_tool_use hook (plugin/impeccable/hooks) failed, ignored ... ]
model       rows=13-14  matched
```

So the failures are not parsing or grouping: the model simply does not recognise every row that begins with a tool glyph. The reason is arithmetic rather than mysterious — the training batch held **47 tool rows against 3,472 text rows**. A linear model can learn "starts with ♦ means tool call" from that, but it is competing against a class that is 74 times larger, and one row whose shape it has not seen before tips the other way.

The fix is not a better feature. It is more tool rows: the class needs to be measured in hundreds before the model can be trusted on it, and the corpus builder already has the scenario recipe that produces them.

`ui-lm-capture page --model models/page.json` was added for exactly this kind of comparison: the reader and the model describe the same frame, through the same builder, and the difference is the model.

## More data did not fix tool calls; two features did

Doubling the corpus (189 pairs, 7,508 rows) left tool-call reproduction at 52% on a fresh batch — so the hypothesis "the class needs more examples" was wrong, and worth recording as wrong.

A second hypothesis was also killed by measurement: the tool glyph might have been arriving mangled by the pty host's decoding. Counted across the evaluation batch: **82 clean ♦ and 0 mangled**. The glyph was never the problem.

What fixed it was giving the model something to see besides the glyph: whether a row starts with a non-ASCII symbol, and whether it names a tool (`hook`, `Edited`, `Read`, `Ran`, `Wrote`). With those two features:

| | before | after |
|---|---|---|
| held-out tool-call recall | 52.6% | **100%** |
| page score, unseen batch | 82.3% | **85.5%** |
| tool calls reproduced | 25 of 48 | **39 of 48** |
| meters / reasoning | 61 of 61 / 9 of 9 | unchanged |

```
model 85.5%  floor 41.5%  over 93 frame(s), trained on 189 screen(s)
  Block      287/389 reproduced
  Meter       61/61  reproduced
  Thought      9/9   reproduced
  ToolCall    39/48  reproduced
```

The general lesson is about where to look: a component scoring badly is more often a *blind spot in the features* than a shortage of examples, and the only way to tell the two apart is to change one thing and re-measure.

## The box was being cut into rows

Blocks were the worst component — 74% while meters and reasoning lines were perfect. The cause was in my own grouping rule: a run was split at **any** border character, so a bordered panel became one block per row instead of one block.

Splitting only at the borders that *open* and *close* a box — a vertical bar is the side of a box, not a boundary between two things — gave:

```
model 97.2%  floor 42.9%  over 98 frame(s), trained on 157 screen(s)
  Block      375/394 reproduced
  Meter       64/64  reproduced
  ToolCall    40/43  reproduced
```

| component | before the fix | after |
|---|---|---|
| Block | 74% | **95%** |
| ToolCall | 81% | **93%** |
| Meter | 100% | 100% |
| page score, unseen | 85.5% | **97.2%** |

Three-quarters of what remained was one wrong character in a condition. The model did not change at all; the same weights, the same features.

## Where the numbers come from

- Training: 157 pairs from two independent corpus runs.
- Evaluation: a third corpus run, recorded afterwards, 98 frames — never seen in training.
- Floor on the same frames: **42.9%**, from a converter that only splits paragraphs.

## Outside the application it was trained on

`scripts/build-nongrok.ps1` records four screens from programs the model has never seen: a drawn inventory panel, an edit report of minus and plus lines, a file listing, and the operating system's own `dir`.

```
model 83.3%  floor 83.3%  over 4 frame(s), trained on 157 screen(s)
  Block      6/6 reproduced
  Diff       0/1 reproduced
```

Two things, one reassuring and one not:

- **The model loses nothing** on unfamiliar applications — it matches the floor rather than falling below it. But these screens are simple, so tying the floor is the most that can be said; it is not evidence of general skill.
- **The model cannot produce a `Diff` at all.** Training held 7,508 rows and not one of them was a diff line, so the component is invisible to it. The reference page found one; the model found none.

That is the honest shape of the result: the model is good at what it has seen and blind to what it has not, which is exactly what a linear model over hand-chosen features should be. Fixing it is a data question — diff screens have to be recorded.

The evaluation set is deliberately **not** committed (`/eval/` is ignored) for the same reason the corpus is not: a recorded screen carries the machine it was recorded on.

## One command now records, trains and evaluates

`scripts/retrain.ps1` does the whole cycle so the numbers come from the same code every time: two training batches plus edit screens, an export, training, then two evaluations — a fresh batch from the training application and a batch from other programs.

```
pairs: 205  rows: 8128
rows per kind: Block=7836, ToolCall=108, Meter=144, Thought=36, Diff=4
row accuracy — train 98.2%, held out 98.2%
  Block 98.4%   ToolCall 77.8%   Meter 100.0%   Thought 100.0%

=== unseen batch, training application ===
model 94.5%  floor 33.4%  over 113 frame(s)
  Block 373/388   Meter 72/72   Thought 2/2   ToolCall 59/69

=== unseen batch, other applications ===
model 83.3%  floor 83.3%  over 4 frame(s)
  Block 6/6   Diff 0/1
```

## Diff is still not learned, and the reason is arithmetic again

Four diff rows in eight thousand. The model cannot produce a component it has seen four times, and no feature will fix that — the training set has to contain dozens of edit screens before a `Diff` is something the model could emit. The earlier reading of the same batch (before diff screens were added) gave the same 0 of 1, so this is not a regression; it is simply untouched.

## What is steady across three independent evaluations

| evaluation batch | model | floor |
|---|---|---|
| 93 frames | 85.5% | 41.5% |
| 98 frames | 97.2% | 42.9% |
| 113 frames | 94.5% | 33.4% |

Every one is a batch recorded after training, never seen by the model. The model sits between 85% and 97% while doing nothing sits between 33% and 43% — the margin is large and it does not depend on which batch is used.

## The Diff was never built, not never learned

A dozen varied edit screens took diff rows from 4 to 28, and held-out diff recall went to 100% — yet the component still scored 0 of 1. The cause was in the builder: `body_for` had no branch for `Diff`, so a row the model correctly called a diff could only ever become text. Adding the branch, with the same rule the reader uses (a run is a diff only if it really holds both removals and additions):

```
=== other applications ===
model 100.0%  floor 83.3%  over 4 frame(s)
  Block 6/6   Diff 1/1

=== training application ===
model 94.9%  floor 44.3%  over 83 frame(s)
  Block 338/351   Meter 51/51   Thought 16/16   ToolCall 36/43
```

| component | before | after |
|---|---|---|
| Diff (other applications) | 0 of 1 | **1 of 1** |
| model, other applications | 83.3% | **100.0%** |
| model, training application | 94.9% | 94.9% (unchanged) |

That is the fourth bug of this kind — after block grouping, reasoning classification and the box split: **the model was right and the assembly was not.** Three of the four were found by the page score and none by a unit test.

## Outside the training application, on screens with structure in them

The first cross-application test was worthless: four screens holding almost no structure, where the model tied the floor at 83.3% and that meant nothing. The screens were redrawn the way an application actually draws them — a limit line of its own, a bordered panel, tool lines outside the box, a multi-line edit report, a column table, prose — across five unrelated programs.

What the reader finds in them: 6 blocks, 1 diff, 1 meter, 1 tool call per run.

```
model 100.0%  floor 77.1%  over 8 frame(s), trained on 179 screen(s)
  Block      11/11 reproduced
  Diff        2/2  reproduced
  Meter       1/1  reproduced
  ToolCall    1/1  reproduced
```

**A model trained only on Grok Build reproduced every component of screens from five programs it had never seen** — a storage banner, an inventory panel, an edit report, a column table and a Python traceback.

That is the first evidence in this project that what was learned is a model of *screens* rather than a model of *Grok*. It is still a small test — eight frames, drawn for the purpose — but it is a real one, and it is the number that would have to fall if the model were only memorising.

## Doubling the corpus changed nothing, which is the finding

Four independent recording batches — 342 pairs, 13,320 rows — against the 179 that came before:

| | 179 pairs | 342 pairs |
|---|---|---|
| training application, unseen | 94.9% | **94.8%** |
| other applications | 100% | 100% |
| floor | 44.3% | 39.2% |
| held-out tool-call recall | 70% | 90% |

The page score did not move. Row-level recall did — tool calls went from 70% to 90% — so the extra data taught the model something real, but it did not change what a page is worth.

**That is a plateau, and it is information**: the remaining error is not a shortage of screens. What is left is the linear model's shape — nineteen features, no interactions between rows — and if the score is to move it will have to move there. Recorded here rather than answered by recording another four batches.

## A label decides where a block ends, so it cannot be corrected afterwards

`score --misses` named the misses: the application's session cards, each card one block to the reader and two to the model. `page --labels` named the cause: the card's icon row was labelled `Thought`, because a list glyph looks like a reasoning marker.

The first fix relabelled the row and changed nothing — **to the component, 407/425 before and after**. The reason is worth keeping: a label decides where one block ends and the next begins, so correcting a label *after* the grouping cannot put a split block back together. The guard had to run before `runs`, not after.

Two of the three guards are therefore per row (a list glyph is not a thought; `Design 20/40` is not a meter). The third needs the whole run (a lone `+ New Agent` row is a button, not a diff) and stays after grouping.

| | before | after |
|---|---|---|
| page structure, training application | 94.8% | **95.3%** |
| blocks reproduced | 407/425 | **413/425** |
| other applications | 100% | 100% |

Both diagnostics that found this (`--misses`, `--labels`) were added this session, and neither existed while the previous four rounds of "model" failures were being guessed at.

## The model had no word for what the screen was doing

The miss list said `♦ Explored 1 search`, eight times, on the same screen. `page --labels` said why: the row was labelled `Thought`. The model's vocabulary of tool verbs was `hook, Edited, Read, Ran, Wrote` — it had no word for a search.

Adding three verbs (`Explored`, `Searched`, `Listed`) to the same nineteen features, and retraining on the corpus already on disk:

| | before | after |
|---|---|---|
| page structure, training application | 95.3% | **99.0%** |
| tool calls reproduced | 42/50 | **50/50** |
| held-out tool-call recall | 90.0% | 92.5% |
| other applications | 100% | 100% |

**This is the clearest case yet that features matter more than data.** Four recording batches and 13,320 rows moved the page score by nothing at all; three words in a list moved it by nearly four points. The model was never short of examples — it was short of a name for something.

One hypothesis was tried and dropped on the way: treating rows that hold only a scroll column's block glyph as blank. The reference counts those rows as content, and the score fell 95.3% → 93.6%. Reverted.

Twelve blocks still differ on one screen, all in a pane whose empty rows carry that scroll column. Named, not guessed: the next round starts there.
## Every component reproduced, and why that needs care

Two more structural guards, each the check the reader makes and the model cannot:

- **a meter starts with a number.** `> /import-memory` holds a slash and is the input line;
  labelled a meter it cut its pane from every row below it — twelve blocks on one screen.
- **a tool call carries the application glyph.** `Read notes.txt first line` is the user
  message echoed back, not something the tool did.

| | before | after |
|---|---|---|
| page structure, unseen batch | 99.0% | **100.0%** |
| blocks | 424/425 | **425/425** |
| other applications | 100% | 100% |

The caveat matters more than the number: that batch shares scenario types with training.
Across the five batches on disk the range is **95.0–100%** against floors of 39–45%
(98.2, 97.7, 95.0, 98.8, 100.0). The next real test is a screen type nobody has recorded.
## Screens it was never trained on, because the application was failing

Every scenario in the corpus is the application working normally. `scripts/build-unseen.ps1`
records it going wrong — a command that fails, a file that is not there, three tool calls in
one turn, a failing test run — none of which appear in the 342 training screens.

| session | frames | model | floor | blocks |
|---|---|---|---|---|
| command fails | 13 | 99.8% | 32.8% | 55/56 |
| missing file | 25 | 99.9% | 20.6% | 116/117 |
| long log | 16 | 100.0% | 26.3% | 79/79 |
| failing tests | 19 | 100.0% | 24.2% | 86/86 |

73 frames, 336 of 338 blocks, every meter (59/59), thought (8/8) and tool call (44/44)
reproduced, against a floor of roughly a quarter.

**Why this is the strongest evidence so far:** the earlier numbers could be explained by the
model having learned the shapes of the recorded scenarios. These four are states the corpus
never contained — an error report, an absence, a scroll, a failure — and the model described
them as well as it describes the screens it was built from.
## Real applications, and two ways the model lost to the floor before it matched it

`eval/apps` records tools this project did not write: `gh run list`, `git log --graph`,
`npm ls`, `pip list`.

First pass: **`gh run list` scored 50% against a floor of 100%.** The status column starts
each row with `✓`, and the model called those rows thoughts; a plain table shattered into
seven blocks where the reader saw one. A thought, it turns out, carries both the mark and
the word — `♦ Thought for 0.6s` — so a row with neither is not one.

Second pass: **`npm ls` scored 0% against a floor of 100%.** A package listing row
`-- (empty)` was labelled a diff and split a two-row screen in two. The diff guard existed
but ran after grouping, and a label that decides grouping cannot be corrected afterwards —
the same lesson as the meter guard two rounds earlier.

After both, every set reads the same:

| set | frames | model | floor |
|---|---|---|---|
| training application, unseen batch | 100 | 100.0% | 39.2% |
| failure states never trained on | 73 | 100.0% | 24.9% |
| programs written for the purpose | 8 | 100.0% | 77.1% |
| real applications | 5 | 100.0% | 100.0% |

**The real-application row needs the most care.** Five frames, all plain text, so the floor
is already perfect and the model can only match it — that set can now fail but cannot yet
prove much. It is recorded here as the start of a set rather than as a result.
## The failures, written down as rules a build can check

Every fix this month came from a screen failing in front of me: a table whose status column
uses `✓`, a package listing that says `-- (empty)`, an input line with a slash in it. None of
those screens is in the corpus, so none of the fixes would survive a later change unnoticed.

`crates/pages/tests/guards.rs` now holds ten cases, one per rule: a single added line is not
a diff, a package listing is not a diff, a session card is not a thought, a status table is
not a page of thoughts, an input line is not a meter, an echoed message is not a tool call —
and the positive case for each, because a guard that demotes everything would pass a suite
made only of negatives.

They were mutation-tested rather than trusted. Deleting the thought guard makes
`a_session_card_is_not_a_thought` fail; restoring it makes all ten pass.

One mutation produced no failure and that is worth recording: weakening the diff-run guard
changed nothing, because `body_for` independently refuses to build a diff from a single
added line and falls back to text. **Two mechanisms cover that case**, which is why the
behaviour held while the guard moved — the tests pin the rule, not the mechanism.
## The other direction existed only in the HTML renderer

The project is asked to go both ways. It went one: a screen was read into a page, and the
page was drawn as HTML. There was no page-to-terminal renderer at all, so "GUI to TUI" had
never been built, only assumed.

`crates/render/src/terminal.rs` draws a page back as the text a terminal would show, and
`ui-lm-capture tui --session DIR --all` reports how much of the screen survives the trip. It
is rule-based on purpose: every component carries the text it was read from, so drawing it
back is transcription, and a model here could only add a way to be wrong.

| recording | content lines back |
|---|---|
| purpose-built panel | 6/6 |
| purpose-built edit report | 7/7 |
| `gh run list` | 13/13 |
| `git log --graph` | 18/18 |
| `pip list` | 31/31 |
| failing test run | 563/563 |
| long log | 464/464 |
| whole training batch, 13 sessions | **1986/1986** |

**What this does not prove.** The first measurement said 15% and meant nothing: it compared
whole screens including padding, and a page does not record blank rows — the reader consumes
them as separators. Content and layout are now measured separately, and only content is
faithful. A page drawn back keeps every line the screen said and none of the vertical space
it said them in, which is honest about what the page is: a description, not a copy.

Three fresh recording batches: 262 pairs, 10,120 rows. (Fewer pairs than the 342 earlier,

| fresh batch, training application | 90 | 100.0% | 43.5% |

## The floor cannot make a diff, and for a while neither could the model

`git diff`, recorded from a scratch repository with two changed lines:

```
model 100.0%  floor 0.0%  over 1 frame(s)
```

The floor scores zero because a paragraph splitter has no way to describe an edit. The model
scored zero too, for a different reason: the ten rows of a diff begin with `diff --git` and
`index`, and a model reading one row at a time calls those text — so the run was split and
the change was never offered to the diff reader at all.

The fix is the reader's own rule, applied to a block: **ask whether the run holds a removal
and an addition**, rather than trusting what each row was called. A `Block` that turns out to
be a diff is now built as one.

This is the eighth time a "model failure" was the assembly asking the wrong question, and the
most convincing: a real diff is the one component the catalogue exists for, and both the
floor and the model missed it for opposite reasons.

| set | frames | model | floor |
|---|---|---|---|
| real `git diff` | 1 | 100.0% | 0.0% |
| training application, fresh batch | 90 | 100.0% | 43.5% |
| failure states never trained on | 73 | 100.0% | 24.9% |
| purpose-built programs | 8 | 100.0% | 77.1% |
## A standing check instead of finding the tenth bug by accident

Nine defects this month were the assembly, not the weights, and every one was found by a
screen failing in front of me. `ui-lm-capture self-check` inverts the search: it takes the
reader's own answer for each row, feeds those labels back through the label path, and asks
whether the page comes back identical. Anything less than 100% is a place where the label
path loses something the reader keeps — found without waiting for a screen.

| set | frames | label path rebuilt |
|---|---|---|
| training batch | 90 | 100.0% |
| failure states | 73 | 100.0% |
| purpose-built programs | 8 | 100.0% |
| real applications | 9 | 100.0% |

**What it proves and what it does not.** It proves the path is faithful when the labels are
right, so no further gap of the kind that produced nine defects remains in these frames. It
does not prove the model's labels are right — that is what `score` measures, and the two
commands together separate *judgement* from *construction*, which is the distinction the last
nine rounds kept confusing.
## A rule written for one screen shape has to be as narrow as that shape

Thirteen real applications are now recorded. Eleven read at 100%. `cargo tree` read at 25% —
the same as the floor — because a dependency branch `└── vt100 v0.15.2` was being glued to
the row above it, while the reader gives each branch its own block.

The first fix said: *a closing glyph with any text after it starts a block*. That took
`cargo tree` to 62.5% and the training batch from 100% to **90.5%**, the failure states to
94.9% and the purpose-built programs to 87.5% — because the application's own box closes with
a rule that carries a label, `╰── Grok 4.7 (low) ─╯`.

Narrowed to the branch shape alone (`└──`, `├──`), the three sets returned to 100% and
`cargo tree` sits at **43.8%** — better than the floor's 25%, still not right, and recorded
here as unfinished rather than described as fixed.

**The lesson is the shape of the mistake, not the score.** A guard written for one screen
will rewrite every other screen unless it is as narrow as the shape that motivated it. The
first version of this rule was plausible, measured, and wrong in a way only the other three
sets could reveal.
## Finishing the tree: two rules, each narrowed by measurement

`cargo tree` went 25% → 43.8% → 62.5% → **100%** in three measurements, and each step was
decided by what the reader does, not by what looked right:

1. **A branch row starts its own block** — but only the last one in a group. Splitting at
   `├──` as well took the training batch from 100% to 90.5% and the screen only to 43.8%;
   splitting at `└──` alone reached 62.5% with everything else still perfect.
2. **A `└──` row also closes its block.** Without that the row after a branch was glued to
   it (`└── vt100` + `[dev-dependencies]` as one), which was the last 37.5 points.

| set | frames | model | floor |
|---|---|---|---|
| real applications, 13 of them | 14 | **100.0%** | 25–100% |
| training application, fresh batch | 90 | 100.0% | 43.5% |
| failure states never trained on | 73 | 100.0% | 24.9% |
| purpose-built programs | 8 | 100.0% | 77.1% |
| `self-check`, real applications | 14 | 100.0% | — |

Every recording on this machine now describes at 100%, against floors between a quarter and
a half. That is the state to be suspicious of, and the next section says why.
## A full-screen application, and the ceiling the catalogue puts on it

Recorded through WSL: `vim` opening a file, writing, and splitting into two panes; and vim's
help window. Software nobody in this project wrote, with panes, a status line, its own
borders and a cursor.

| measurement | result |
|---|---|
| model on vim screens (5 frames) | 100.0% |
| floor on vim screens | 100.0% |
| reverse direction: content lines returned | 176/176 (100.0%) |

**The forward number proves almost nothing, and the reason is the finding.** The floor ties
at 100% because the reader finds *one or two plain blocks* in a screen holding two panes, a
status line, a ruler and a column of tildes. Everything vim draws that a person would call
structure — the split, which pane has focus, the ruler, the mode indicator — is not in the
page, so a model reading the page cannot put it there either.

That is the honest limit of this stage of the project: **the model is only ever as good as the
vocabulary it fills in.** Ten rounds of measuring the model against the reader measured it
against a reader that describes terminal text well and full-screen applications barely at
all. On Grok Build's screens the vocabulary happens to fit, which is why the numbers are high.

The next real work is not in the weights, the guards or the corpus. It is in the catalogue:
a full-screen application needs at least a frame with panes, a focused pane, a status line
carrying mode, and a ruler. Until the page can hold those, "TUI to GUI" for a TUI application
means "TUI to GUI for a TUI's text", which is not the thing the project set out to do.
## Slice 1 of the design: the reader now sees panes

A split `vim` used to be one opaque block of thirty rows. The reader now splits a screen into
panes when, and only when, all three hold: the screen is a single block, it carries no box
borders, and a column of `|` or `│` runs down at least six rows in ten.

| screen | before | after |
|---|---|---|
| vim, vertical split | 1 Block | **2 Blocks, `role = "pane"`** |

**Nothing else moved.** Training batch 100% (90 frames), failure states 100% (73),
purpose-built programs 100% (8), all 13 real applications 100%, `self-check` 100%, full test
suite green.

### What this slice does not do, measured rather than assumed

The reader improved and the rest of the pipeline did not, so the numbers say so:

| measurement | result |
|---|---|
| model on vim vsplit | 33.3% — **tied with the floor** |
| model on vim, plain | 66.7% — tied with the floor |
| reverse direction on vim vsplit | 32.6% of content lines (was 100%) |

Two gaps, both created by this change and both next:

1. **The label path has no pane logic.** `page_from_labels` builds components from labels
   alone, so a model filling that path cannot produce a pane however good its labels are.
   Until it can, the model scores exactly what the floor scores on any split screen.
2. **The renderer draws panes one after another.** Left pane, then right pane, stacked — so
   the round trip that was 100% fell to 32.6% on the same frames. Panes have to be drawn
   side by side, or the page is describing something the renderer turns back into a column.

Recording both as gaps rather than reporting the reader's win as if the pipeline had improved.
## Finishing the panes: the width is part of what a pane says

The renderer drew panes side by side and the round trip still read 32.6%. Three fixes, each
one a measurement:

1. **The left pane keeps its width.** Trimming it put every row at the wrong column — the
   content was all there and the layout was gone.
2. **The left pane absorbs the divider character.** Joining with a `|` invented the divider
   on rows where the screen had a space there, and missed it where a row was short.
3. **The merged row is right-trimmed.** A short row padded out to the pane width came back
   padded, which is not what the row said.

| measurement | before | after |
|---|---|---|
| round trip, vim vertical split | 32.6% | **100.0%** (89/89 lines) |
| round trip, vim plain | 100% | 100% (108/108) |
| model on vim vertical split | 100% | 100%, floor 33.3% |
| every other set | 100% | 100% |

Both directions now describe a split application correctly: the page holds two panes, the
model fills them, and drawing the page back returns every line in its place.
## The bet on roles, tested on a second application

The design deferred a `Frame` component and used `role = "pane"` on a block instead, on the
strength of **one** application. That was a bet, and this is the screen that settles it: `tmux`
drawing its own panes and status bar, written by nobody here.

**It worked with no code change.** The same three conditions — one block, no box borders, a
column of `|` down most rows — found tmux's panes exactly as they had found vim's.

| screen | panes found | model | floor | round trip |
|---|---|---|---|---|
| vim, vertical split | 2 | 100.0% | 33.3% | 89/89 (100%) |
| tmux, two panes | 2 | 100.0% | 25.0% | 92/92 (100%) |
| vim, plain | — | 100.0% | 66.7% | 108/108 (100%) |
| nano | — | 100.0% | 100.0% | 4/4 (100%) |

`crates/pages/tests/fixtures/screens/tmux-two-panes.txt` holds the screen, and
`a_second_full_screen_application_splits_without_new_code` fails if a future change makes the
rule vim-specific.

**What this does and does not establish.** It establishes that the pane shape is a property of
full-screen applications rather than of vim — two applications, one rule, no special case. It
does not establish that a `Frame` component is unnecessary: tmux and vim both put panes side
by side in a plain rectangle, and neither has a floating window, a tab strip inside a pane, or
a pane that scrolls independently. The design's next trigger stands: a third application with
a shape these roles cannot express.
## A screen that changes, and the rule that was quietly broken

`top`, recorded live rather than in batch mode, is the first screen here that keeps drawing
while it is described: ten frames, twenty components, four of them repeated from earlier
frames.

`ui-lm-capture provenance` now checks the project's oldest promise — a component whose text
appeared in an earlier frame is `carried`, one whose text is new is `seen` — and it found
**2 contradictions in 967 components**, both in a split vim session.

The cause: pane components were built with `Seen` unconditionally. Three identical frames of
a split screen each claimed they had read the same content off the cells. The score never
noticed, because a page can be perfectly accurate in its *first* frame and dishonest in its
second.

Fixed, and every recording now checks clean:

| | components | carried | contradictions |
|---|---|---|---|
| all recordings | 967 | 544 | **0** |

That is the fourth diagnostic added this month (`--misses`, `--labels`, `self-check`,
`provenance`), and like the others it found something no score could see.

## A perfect score that carried no colour at all

The quietest claim in this project is that a page holds what the screen looked like, not only
what it said. Measured across the training batch: the reader carries **6,303 spans**; a page
the model built carried **0**. Every page the model described would have rendered in one
colour, and no score noticed, because `compare` reads structure and text and nothing else.

Two defects, found in the same measurement:

1. **`page --all --model` silently ignored the model.** It printed exactly what `page --all`
   prints without it, so a request that asked for the model got the reader and no warning.
   Fixed; `--all` now describes every frame with the model and carries provenance across them.
2. **The model's page had no styling.** Fixed by grafting the recorder's spans onto the page
   the model judged — the division this project already states, judgement from the model,
   construction from the code that watched the screen.

| | before | after |
|---|---|---|
| spans on model pages | 0 | **6,303 (identical to the reader)** |
| `--all` honouring `--model` | no | yes |

This is the fifth defect found by checking a claim rather than averaging a result, and the
first that would have been invisible in a screenshot until someone compared colours.
## The styling reaches the browser, and one path could not reach it at all

Checked the last link: does the drawn page use the spans it holds?

| measurement | result |
|---|---|
| styled spans in the HTML | 162 |
| colour declarations | 292 |
| bold, italic, dim | all emitted (`font-weight:700` and friends) |
| model pages drawn by `render` | **not possible** — the flag did not exist |

So the reader's page reaches the browser with its colours, and the model's page could not be
drawn at all: `render` had no `--model`, exactly like `page --all` one round earlier.

That is now the second flag this month that existed on every command but one. Both were found
by asking a question about the product rather than about the model: *what does a person
actually open?* The answer is the HTML file, and until this round it could only ever show the
reader's judgement.

`render --model` builds every frame with the model, grafts the recorder's styling, and keeps
provenance across frames. Verified: a missing model file fails loudly rather than silently
falling back, and the HTML carries the same 162 styled spans as the reader's.
## The third path, and the same defect for the third time

Asked one layer further out — *what does the live viewer show?* — the answer was the model's
judgement in the reader's colours, which is to say: no colours at all.

| path | before | after |
|---|---|---|
| `page --all --model` | ignored the model | uses it |
| `render --model` | the flag did not exist | draws model pages |
| **`serve --model`** | model page, **no spans** | **162 styled spans in the served HTML** |

`graft_spans` now lives in the page crate, because three different programs needed the same
rule and had been getting two different answers:

```
screen → reader ──┐
                  ├→ page (structure + text + spans) → HTML / terminal / live view
       model  ────┘
```

**Three appearances of one defect — a capability that exists on one path and silently not on
another — is no longer an accident.** The CLI, the file and the live view are three front
doors to the same page, and each was built at a different time by the same person with the
same blind spot. The rule that follows: any place a page is built must be able to say which
of judgement and styling it received, and a missing one must fail loudly rather than quietly
render grey.

Verified after the change: capture 285 spans on the model path, the live server serving 162
styled spans, clippy, fmt and the whole test suite clean.
## The live view under a screen that changes

Every test until now read a recording. This one watched `top` while it was being recorded, with
the viewer polling the running pipeline:

| poll | frames | components | carried | styled spans |
|---|---|---|---|---|
| 1 | 9 | 2 | 0 | 22 |
| 2 | 11 | 2 | 1 | 22 |
| 3 | 13 | 2 | 1 | 23 |
| 4 | 15 | 2 | 0 | 23 |
| 5 | 17 | 2 | 0 | 23 |

Frames advance, the page changes, the colours arrive, and nothing stalls.

**One thing did not work, and it was a design hole rather than a bug.** The live view served
only the newest frame, so every component was `seen` and a viewer could never tell what had
stayed on screen. Provenance now advances against the last page the browser *received* — poll
2 shows `carried = 1` because the process table was still on screen, poll 4 shows `0` because
both components had changed.

The first attempt got this wrong in an instructive way: it updated the "previous page" on every
read rather than every delivery, so a static screen never marked anything carried. **Provenance
is a statement about what someone saw, not about what the program computed**, and the fix was
to move it to the moment of delivery.
## How much of the evidence actually tests anything

Four workflows recorded that were not chosen for their shape: `ps aux`, `df -h` with `free`,

four describe at 100%.

**So does the floor.** Every one of these screens is plain text with one block, which a

That is worth stating as a number rather than a feeling:

| | count |
|---|---|
| evaluation sessions | 37 |
| sessions where the floor already succeeds | **24** |
| frames | 134 |
| frames in sessions that can discriminate | **93 (69%)** |

**Two thirds of the evidence can fail; one third cannot.** The 100% figures across this month

The honest reading: this project's real test is the 93 frames with diffs, meters, panes and

One recording also failed the first time — `ps aux | head` exited before a frame settled — and

## The third full-screen shape, and why the vocabulary stopped there

The design deferred a `Frame` component until a third application showed a shape roles could
not express. Recorded: **vim with a tab strip and two windows**, and **`man`**, a pager with a
status line and no panes.

What the page says about vim's tab strip:

```
/t/u/one.txt  /t/u/two.txt                            X
```

That is a `Block` with role `text`. A runtime draws two file names, not two tabs. The reader
is not wrong — those characters really are a line of text — it simply has no vocabulary for a
tab strip that is drawn this way.

**An attempt to fix it was written, run, and thrown away.** The existing `tabs` field looks for
names above a horizontal rule, which is how the agent's overlay draws them; the extension tried
"a numbered first line with no rule under it". It detected nothing, because vim does not number
its tabs here: the strip is two bare paths separated by spaces, and two bare paths are not
distinguishable from two words. A rule that fires on nothing is not a fix, and guessing a
heuristic to catch one application's exact spacing is how vocabulary gets invented badly.

So the trigger the design named has now been reached — **three applications, one shape the
roles cannot express** — with the difference that the missing piece is a *tab strip*, not a
`Frame`. That is a smaller, better-evidenced change than the one the design anticipated, and it
is the next round's work: design `tabs` for the numbered-or-not strip, with vim, `man` and the
agent overlay as its three screens.

| screen | what the model scored | floor |
|---|---|---|
| vim with tabs and splits | 100.0% | 100.0% |
| `man` | 100.0% | 100.0% |

Both floors are 100%, so neither number means anything: this round's evidence is what the page
says, not what the score says.
## Numbered tabs, and a regression that had nothing to do with them

A third full-screen shape was recorded with a tab strip an editor actually numbers —
`1 one.txt  2 two.txt` — and the reader now finds it: `Block tabs=[one.txt, two.txt]`. The
rule demands a number on **every** field, so a table's first row stays a table row, and a test
holds both halves of that.

Then the sweep found `unseen-fail` at **99.8%**, down from 100%. I assumed the new rule had
misfired, checked, and found no tabs anywhere in that session. So I stashed the change and
re-scored: **99.8% without it too.**

**The regression is older than this round and was not caused by the tab rule.** It slipped in
during one of the pane or provenance changes and went unnoticed because those rounds re-scored
the sets they were working on rather than all of them. That is the honest cost of measuring
selectively, and it is the reason the fresh-batch habit exists.

The remaining defect is one block holding rows of `█` — the scroll column — in a failure
screen. It is the same shape that defeated an earlier attempt at a blank-row rule, and it is
next round's work.
## Three attempts at the `█` block, none kept, and what the third one cost

The defect is precise now: on a PowerShell failure screen the reader makes **one** block of
rows 10–22, and the model makes **five**. The rows are error text, `+`-prefixed continuation
lines, and empty rows carrying the scroll column.

| attempt | result |
|---|---|
| label `█`-only rows `Block` consistently | 99.8%, no change |
| require a diff to have both an addition and a removal | 99.8%, no change |
| fold adjacent runs that settle to the same kind | **65.7% — reverted** |

The third is the instructive one. It looks tidy and it is far too broad: it folds every pair of
adjacent runs that agree once settled, so runs that merely resemble each other — two reasoning
lines, two tool lines — become one component. **A rule that merges by resemblance destroys the
distinctions the page exists to make**, and the score said so immediately.

Nothing was kept. The tree is at the baseline, every test passes, and the defect is recorded
rather than papered over. The right fix is narrower than all three: fold *only* a demoted diff
into its immediate neighbours, and leave every other run alone.
## The fix was to stop letting a label decide where blocks end

Three rounds of folding failed. The reason is now clear and it is structural: **a diff is a
property of a finished block, not a reason to start a new one.** The reader never splits on
`+` lines; it builds a block and then asks whether the block is a diff. The label path had the
two the other way round, so PowerShell's `+`-prefixed error text split one block into five,
and every attempt to fold the pieces back cost points somewhere else:

| attempt | result |
|---|---|
| label `█` rows consistently | 99.8%, no change |
| require a diff to have both sides | 99.8%, no change |
| fold adjacent runs that settle alike | **65.7% — reverted** |
| fold only a demoted diff into neighbours | **98.9%, and three other sets broke** |
| **a diff never groups; `as_text` decides afterwards** | **100%, everywhere** |

Verified after the change:

| check | result |
|---|---|
| every eval session (37 sessions) | 100.0% |
| real `git diff` | 100.0%, floor 0.0% |
| fresh batch, 92 frames | 100.0%, floor 42.9% |
| fresh batch, 94 frames | 100.0%, floor 40.1% |
| `self-check`, 114 frames | 100.0% |
| `provenance`, 449 components | 0 contradictions |

**The general lesson, which cost four attempts to learn:** when a description splits something
the reader keeps whole, the fix is almost never to merge the pieces afterwards. It is to stop
the split from happening — and to ask which decision was being made in the wrong place.

## Trained on one application, perfect on every other one

The corpus is 262 screens of **one** application — Grok Build's transcript — plus eight
full-screen pairs. Two questions follow, and both now have measured answers.

**Does full-screen training material matter?** A model trained with those eight pairs removed
scores **100.0% on 41 vim, tmux and nano frames** (floor 78.0%) — exactly what the shipped
model scores. The pane is found by the reader's own rule and built by the label path; it was

**Does the model generalise off its one application?** Trained on those 262 Grok screens and
nothing else, scored on programs it has never seen:

| set | frames | model | floor |
|---|---|---|---|
| `nongrok`, programs written for the purpose | 8 | 100.0% | 77.1% |
| real applications (`gh`, `git`, `npm`, `pip`, `cargo`) | 14 | 100.0% | 87.5% |

**141 frames from software the model was never trained on, every component reproduced**, with

That is the claim this project set out to test — that a model of *screens* can be learned from

## Real developer output, and where structure actually comes from

Ran the shipped pipeline on material nobody scripted for it: a full `cargo test --workspace`
of this project, streamed through the live viewer; and a deliberately **failing** test run in a
throwaway crate.

| | frames | model | floor | round trip | provenance |
|---|---|---|---|---|---|
| live `cargo test` stream | 6 | 100.0% | **100.0%** | 190/190 lines | 48 components, 0 contradictions |
| failing tests | 1 | 100.0% | **100.0%** | — | — |

Every number is perfect and none of them means much: **the floor ties on both**, because a
build log and a test failure are plain text, and a paragraph splitter reproduces plain text
exactly. The failing run even contains `left:` and `right:` lines — the shape a person would
call a diff — and the reader correctly declines to call it one, because it is not drawn with
`+` and `-`.

That is the finding, and it sharpens where this project matters:

**Structure comes from agent transcripts and full-screen applications, not from compiler
output.** Diffs, meters, tool calls and panes are drawn by software that renders state; a build
log renders words. The model's value is confined to the first kind of screen, and on the second
kind it cannot be measured at all because there is nothing to get right.

A second, smaller finding: the recorder captures a frame when the screen **settles**, so a
30-second build produced six frames. A live viewer over fast-moving output sees far fewer
moments than the program actually drew — worth knowing before anyone reads "live" as
"continuous".
## A corpus from more than one application, and why it does not exist

The last open item was the corpus being one application's screens. Recording seven more programs
for training — vim with line numbers, vim split, tmux with two panes, `gh run list`,
`git log --graph`, `pip list`, `cargo tree` — yields **eleven pairs and not one structured
screen**:

```
0 of 11 pair(s) hold a meter, a tool call, a diff or a reasoning line
pairs written: 0
```

Twenty-six components across those seven programs, all of them `Block`. Nothing to train on.

**The corpus is one application for a reason that is not an oversight.** A meter is a quota
drawn against a limit, a tool call is a marked action, a diff is an addition beside a removal,
a thought is a folded reasoning line — all of them are drawn by software that *renders state*.
Editors, pagers, package listings and dependency trees render *text*. There is no component in
them to learn, which is why `dataset` writes nothing for these screens by default.

So the answer to "would a mixed corpus read better?" is **there is nothing to mix in**, and the
limitation recorded in the README is better stated as: *the training material is one agent's
transcripts because only agents draw the components this catalogue is for.* That is a property
of the problem, not a gap in the work.
## The interactive path, which nothing had tested

Every check in this project until now read a recording. `scripts/check-interaction.ps1` runs the
two processes the README describes — a recorder and a viewer — and types into the viewer over

```

```

The program ran the text, the screen gained a frame, and the page contained the output. That is

It fails with exit code 1 if the text never appears or if no frame arrives, so it can gate a

## The two ways a live recording can be read at a bad moment

`scripts/check-race.ps1` exercises both:

| race | result |
|---|---|
| 140 reads of `/state` while frames were being appended | **140 answered**, frames 3 → 4, never went backwards, viewer alive |

## A big screen, an empty page, and what it turned out to be

A 200-row screen of thousands of lines described as an empty page. Probing heights found no
threshold — 110, 128, 150 and 180 rows all gave nothing, 129 gave fifteen components — which
ruled out a size limit and pointed at timing: **the final frame of a run is often blank**, and
the page of a blank frame is correctly empty.

That is a real product problem even though the page is right: a viewer that serves the newest
frame goes blank at the moment a person stops looking at their program. The viewer now serves
the newest frame that carries a component, falling back to the last one when every frame is
blank.

**Verification of that fix is incomplete, and this is where I say so.** The change builds, the
suite passes, and a direct reading of both frames shows the program's output present — but the
live probe I ran to confirm the served page contained that output reported `False` while the
page itself did contain it. One of the two readings is wrong and I have not yet established
which. The fix is conservative and tested; its end-to-end confirmation is next round's work.
## The contradiction resolved: the fix was right, my probe was wrong

Last round ended with a served page that a direct read said contained the program's output and a
live probe that said it did not. The probe was wrong. Reading the raw response and comparing it
to every recorded frame settles it:

```
frames: 3
  frame 0: components=0   hasMarker=False     <- the shell prompt, blank
  frame 1: components=1   hasMarker=True
  frame 2: components=0   hasMarker=False     <- Clear-Host, the last thing it did
last frame blank: True
served shows the marker: True
served page equals blank last frame: False
```

A program whose final action is to clear the screen leaves a blank newest frame, and the viewer
now serves the last one with content instead. That is the case the fix was written for, and it
is now in `scripts/check-race.ps1` alongside the redraw and half-written-frame cases:

```
reads during a redraw: 140/140 answered, frames 3 -> 4
half-written frame: 1 session(s), 3 frame(s), 3 distinct screen(s)
screen cleared at exit: the viewer kept CLEARED-MARKER-729
the viewer survives a redraw, a half-written frame, and a screen cleared at exit
```

**The lesson is about the verification, not the fix.** A probe that printed one word was
treated as evidence for a round; reading the response and comparing it to the frames took ten
minutes and was conclusive. When two readings disagree, the cheap one is usually the liar.
## The renderer is fine; the live HTML stopped changing

Under load the renderer holds: **81 pages, 315.6 KB, 359 ms**, well-formed, 1,584 styled spans.
Sixty fetches of the live page during a redraw came back complete and untruncated.

Then a closer look found something the first test hid: **every one of those sixty responses was
byte-identical**, and a second run confirmed it — six polls, frames 25 → 51, **one HTML hash**.

The renderer is not the cause: rendered from the CLI, frame 1 and frame 6 differ (3,663 and
4,958 bytes). So the live snapshot is serving a page that stopped changing while frames kept
arriving.

**The likely cause is the rule added last round**, which serves the newest frame that "carries a
component". If an early frame is the last one whose page has a component — because later frames
of a scrolling screen describe as something the check counts as empty — the viewer pins that
early frame and never moves again. That fits every observation: frames advance, the page does
not.

Recorded as an open defect rather than fixed in passing. The rule was added to stop the viewer
going blank at exit; it now appears to freeze it instead, and the fix needs the same care as the
tests that caught it. Next round starts here.
## The freeze did not reproduce, and the claim is withdrawn

Last round reported that the live page stopped changing while frames advanced. Two careful
trials do not reproduce it:

| | frames | page contains the program's output |
|---|---|---|
| live, mid-recording | 31 | **yes** |
| live, after the program exited | 41 | **yes** |
| static recording | 16 | **yes** |

The live view updates, and it carries what the program printed. The earlier evidence was thin in
a way I should have noticed at the time: one run compared HTML *sizes* (all identical, which two
different pages can easily be), and the other compared SHA-256 prefixes that were identical in
their first characters — a probe I had already seen lie once this month, in round 55.

**So the defect reported last round is withdrawn**, not fixed. The rule that serves the newest
frame with content stands, and the cleared-screen case it was written for still passes.

What is missing is the check that would have settled it in a minute: a test that asserts the
served HTML *changes* while a recording is being written. That is next round's first job, and it
belongs in `check-race.ps1` beside the other three.
## A check with a control, because three attempts had none

`scripts/check-live-page.ps1` answers the question that produced a false alarm and one check that
silently did not run: **does the live page change while the program draws?**

It prints the two sizes it compared on every run, so a silent skip is impossible, and it carries
its own control — the same comparison against a finished recording must come out *equal*:

```
live page: 5086 bytes, then 5086 bytes        <- control: finished recording
a finished recording holds still, as it must
the live page changes while the program draws
```

Both directions were exercised. With the program changed to draw once and sleep, the same script
fails and says why:

```
live page: 4512 bytes, then 4512 bytes
the page did not change across three seconds of a drawing program
exit 1
```

**An instrument that cannot fail is not an instrument**, and the control is what makes the pass
mean something: it proves the check can tell "changed" from "did not change" rather than
reporting motion for any page at all.
