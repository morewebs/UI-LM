# The loop, end to end

Date: 2026-10-27. The first run in which a person pressing a button on a page reached a
running program and came back as a new screen.

## What was run

A small program drew two shortcut rows — `Resume Session … Ctrl+R`, `Agent Dashboard …
/dashboard` — then waited for a raw key. It was recorded with `--control`, the recording was
served by `ui-lm-serve`, and the page's `Ctrl+R` button was pressed.

## What came back

| step | evidence |
|---|---|
| the page drew buttons | `data-binding` values `Ctrl+R`, `/dashboard` |
| the press reached the viewer | `POST /keys?binding=Ctrl%2BR` → 204 |
| the press reached the recording | the control file held exactly one byte, `0x12` |
| the program answered | a new frame containing `GOT CTRL+R` |

`Ctrl+R` is `0x12`: the byte a terminal sends for that chord, not the letters "Ctrl+R".

## Two things the first attempt got wrong

Both were in the test harness, and both are worth keeping because they are what a person
building on this will hit:

- **A pty is line-buffered until the program asks otherwise.** A lone `0x12` sat in the
  kernel's buffer and never arrived, because the program had not put its terminal in raw
  mode. A real TUI does; a script that reads stdin without it waits for a newline that a
  button press will never send.
- **The rows have to be right-aligned to be read as shortcuts.** Keys of different lengths
  starting at the same column end at different ones, and the page reader groups a column by
  where it ends.

## What this does not establish

The program here is a fixture written for the occasion, not Grok Build. An earlier attempt
against the real application ended before its overlay was drawn — the process was terminated
by a console control event — so the same loop has not been observed against Grok Build. The
plumbing is the same code either way, and that is what this proves.
