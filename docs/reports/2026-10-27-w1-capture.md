## The probe that shaped the harness

One session was captured before the scenario table was written. It answered the
question the whole harness depended on — whether the real application can be
driven non-interactively and stopped — and the answer was no, not the way the
brief assumed.

The probe drove `grok` with a three-word prompt at 6 s, then Ctrl-C twice and a
typed `/exit`. It recorded **37 frames** and then never ended: the recorder was
still running 149 s later and had to be killed, which left frames and no record.
The last settled screen it captured, decoded from `frames.jsonl`:

```
Simple three-word greeting request
> say hi in three words
  Hi there, friend.

Resume this session with:
  grok --resume 01a17cec-c57a-7dc1-9162-f0534bcc1806
```

So the application *was* drivable — the prompt went in, the turn ran, the answer
came back, and the frames are readable — but it would not leave on Ctrl-C.
A second probe confirmed Ctrl-D and a typed `/quit` do not leave either (6 frames
in 10 s, then silence; killed at 75 s). A third probe found the exit that works:
`/exit` at 8 s ended the recorder at 8.3 s with 6 frames **and** a `session.json`.
Every scenario therefore ends with an exit tail — two Escapes to close whatever is
open, then `/exit` twice, because the first is swallowed if a turn is still
generating.

## The folder-trust card, which every session has to answer first

A fresh working directory makes the application open with a card instead of a
prompt:

```
≡ master ~/A/L/T/u/cwd/s24-tool-read

            Do you trust the contents of this directory?
      C:\Users\moreweb\AppData\Local\Temp\ui-lm-w1\cwd\s24-tool-read
   Grok Build may run or modify contents in this directory,
                posing security risks.
```

While that card is up, **keystrokes aimed at the prompt are swallowed**. The first
full run of this capture ran without answering it and produced 36 sessions that
looked plausible and were worthless: the card took the scenario's first input, and
most sessions then ended at their first Escape having captured nothing but the
card. The first runs also showed the card being answered by whatever Enter happened
to arrive, which is why `~/.grok/trusted_folders.toml` accumulated an entry per
session.

`capture-w1.ps1` now prepends one prologue keystroke to every scenario — Enter at
4.5 s — which answers the card. **The card is in the frames of 19 of the 35
sessions, not all of them.** Decoding every frame of every session and looking for
`trust the contents` in its rows gives 19 sessions with the card (each at frame
`seq` 2) and 16 without. The split is not random: the application draws the card
only for a directory it has not already been told to trust, and earlier passes had
already trusted most of these scratch paths. The 14 entries the leaked snapshot of
the first passes (`%TEMP%\ui-lm-w1\trusted_folders.original.toml`, since renamed
`…original.toml.not-pristine-2026-10-27.bak`) holds name 14 of these sessions'
directories, and those 14 sessions are among the 16 that open straight onto the
welcome card — no session that shows the card was in that list, and the other two
sessions without a card (`s24-tool-read`, `s27-tool-write`) were trusted in a pass
whose entries were gone by the time that snapshot was taken. So the dirty trust file
was not only a change to the machine owner's configuration: it changed what 16 of
the 35 sessions recorded.

The trust file itself: `~/.grok/trusted_folders.toml` holds **4 entries**, the four
folders the machine owner had trusted before this task, and nothing under `%TEMP%`.
That is derived, not remembered: the only backup on disk — the leaked snapshot
above — holds **18** entries, the 4 real ones plus **14** naming scratch directories
from this capture, so it is a snapshot of an already-polluted file rather than a
pristine one. Dropping the 14 scratch entries from it reproduces the current file
byte for byte. `capture-w1.ps1`
no longer leaves any of this to a manual cleanup: it snapshots *both* `config.toml`
and `trusted_folders.toml` before the first session, restores both after every
session and again in a `finally` that also runs when the loop throws or the operator
interrupts it, and stops any recorder still alive at that point.

## The frame rate, measured

The recorder's record carries no timestamps (its `seq` numbers frames but does not
time them), so `capture-w1.ps1` samples the growing `frames.jsonl` every 100 ms
while the session runs and notes the arrival time of each frame it sees the file
grow by. That is **519 arrivals for 526 frames**: in 7 sessions two frames landed
inside one 100 ms sample and share one arrival, so the timeline is a lower bound on
the frame count, not one timestamp per frame. Across all 35 sessions, 484 intervals
between consecutive arrivals:

- **First frame** at 115-148 ms after spawn — the blank screen before ConPTY has
  drawn anything.
- **Startup** settles the trust card and then the welcome card: **4-6 frames by
  1.5 s** (4 by 1.5 s in 21 sessions, 5 in 13, 6 in 1), the sixth arriving at about
  4.8 s in 18 of the 34 sessions that reach it — roughly **5 frames a second** while
  the application draws, and then nothing until something is typed.
- **While the application is drawing** (any gap under 2 s), the median gap between
  frames is 328 ms, 90th percentile 769 ms, minimum 107 ms.
  That is the 150 ms settle gap plus the application's own redraw cadence: bursts
  of output, never a stream.
- **While it is idle there are no frames at all.** The median idle gap is
  5.1 s and the longest is 59.4 s, which is a turn that drew nothing for a
  minute. The scenario that held the welcome screen for 22 s on purpose gained
  nothing over the 13 s one: 7 frames against 7.
- The "Waiting for response…" spinner is *not* one frame: its elapsed clock ticks
  about every 0.3 s, so each tick is a settled screen and is recorded as such.

The practical consequence: a scenario's frame yield is set by how often it drives
the application to draw and then pause, not by how long it runs. A 22 s session can
produce the same 7 frames as a 13 s one; a single short prompt produces 6 to 44.

## Surprises

1. **The application writes its UI mode into the machine owner's config file.**
   Passing `--reasoning-effort low` rewrote `default_reasoning_effort` in
   `~/.grok/config.toml`, and pressing Shift-Tab rewrote `permission_mode`
   (`always-approve` → `auto`). Both were caught by an `mtime` change during the
   run and the file was restored to its original 880 bytes; `capture-w1.ps1` now
   snapshots the config before the run, restores it after **every** session, and
   records per session what the app wrote. Without that, later sessions would have
   been captured in a different mode from earlier ones — a silent difference
   between two "identical" screens.
2. **The rig's child does not run in the recorder's working directory.**
   `portable-pty 0.9`'s `CommandBuilder::current_directory()` is
   `cwd.or(%USERPROFILE%)`, and the driver sets no cwd, so every session ran in
   `C:\Users\moreweb` — the first pass of this capture recorded the home
   directory, not the scratch project: file searches found nothing, and one
   scenario created `C:\Users\moreweb\made.txt` (removed; it was 16 bytes,
   `made by capture`). The fix here is the application's own `--cwd <scratch>`
   on every invocation. **The proper fix is in the driver**, which should pass its
   own working directory — that is a Task 1 change, not a capture-script one.
3. **`--fullscreen` produced no alternate-screen frames.** Every frame in every
   session has `alt_screen: false`, including the three sessions run with
   `--fullscreen`. Either the TUI does not switch to the alternate screen at this
   terminal size, or it does and the emulator does not see it. This capture cannot
   tell which, and the alt-screen frame class therefore has **no real-world sample**
   in this set.
4. **`NO_COLOR=1` is inherited from the harness and the application honours it** —
   `grok doctor` says so outright ("Colors are off because `NO_COLOR` is set"). A
   capture taken under it would carry one default colour and no styling. The script
   clears it before every session, and the frames carry truecolor RGB styles
   (`{"fg":{"kind":"rgb","value":[225,225,225]}...}`).
5. **The documented slash menu does not appear in the default TUI at 50x160.**
   Typing a bare `/` echoed the character and produced no menu in 8 s of frames;
   worse, typing `/memory` and pressing Enter silently applied a *completion* —
   `/import-memory` — rather than running the command. In `--minimal` mode the same
   bare `/` draws the full documented menu inline (`/quit quit the application`,
   `/plugins`, `/feedback`, `/model`, `/compact`, `/usage`, `/loop`, `/logout`) with
   a navigation hint. The menu exists; the default renderer does not show it here.
6. **A bare `@` opened no file picker** in the default TUI, contrary to the
   application's own README.
7. **Two plugin hooks fail on every turn** in this environment —
   `session_start hook (plugin/impeccable/hooks) failed, ignored: exit code 1` and
   the same for `stop hook`. They are noise from the machine owner's plugin
   configuration, visible in nearly every transcript because they are drawn into
   the screen. They are recorded as content because they are content.
8. **Two sessions ended with the application reporting `STATUS_CONTROL_C_EXIT`**
   (`-1073741510`): the child died to a console control event of unclear origin, in
   sessions that never sent Ctrl-C — `s20-prompt-text` and `s22-prompt-text-minimal`,
   both of which still wrote their record. The index does not carry that status in
   any structured field: `exit_code` is `null` in **all 35 rows**, because it holds the
   **recorder's** own exit status (and stays `null` when the recorder did not exit at
   all, as for a session killed at its ceiling). What the application reported
   survives only as text: the recorder writes it to stderr, and it is in
   `recorder_stderr` for those two sessions —
   `warning: "C:\Users\moreweb\.grok\bin\grok.exe" exited with status -1073741510`.
9. **Plan mode can wedge the capture.** With `--permission-mode plan`, once the
   plan card is up, Escape, Enter and `/exit` were all tried and none left the
   card; the recorder had to be killed at the ceiling, which leaves frames without
   a record. Answering the card with `n` (the scenario as captured here) is the
   only path that returned to a quittable prompt.

## What this capture does NOT prove

- **K5 is not proven.** Not one frame in this set has been compared against the
  application's own draw buffer. Everything above about "what was on screen" is the
  VT100 emulator's account of it, and the emulator and the application could agree
  on every character of every frame while disagreeing about something this capture
  never looked at. The comparison against the patched fork (task 10b) is the only
  thing that can turn these frames into evidence that the rig records the screen the
  application meant to draw.
- **Cost is not measured.** `SessionRecord.cost` is `null` for all sessions: the TUI
  stream carries no usage events, so nothing priced these runs. The footer does show
  a token counter (`↓1.17k`, `23K / 500K`) and the application has a `/usage` screen
  (captured as `s36-command-usage`), but neither reaches the session record, and no
  dollar figure is invented here. Quota must be read from the xAI account.
- **Volatile spans are empty everywhere.** The recorder passes `event_between: true`
  unconditionally (Task 6's wiring is not done), so `frame.volatile` is `[]` in
  every frame and the spinner's turning characters are recorded as content, not as
  noise. A trainer reading these frames today would train on the spinner.
  **The masking requirement is therefore not delivered in this artefact.** §7.1 calls
  volatile-span masking a rig requirement, and nothing in these 526 frames satisfies
  it: there is no span anywhere in the set, and a frame that cannot say which of its
  cells were spinner noise cannot be masked later either — that information is not in
  the file to recover. **The golden set must not be built from these frames until the
  masking is in the recorder and a capture has been re-taken with it**; building one
  from this set would bake a turning spinner, a ticking clock and a repainting
  progress bar into the training data as though the application had drawn them as
  content. See the section at the end of this report for what has to happen first.
- **The keystroke timing is fixed at script-writing time.** A scenario whose turn
  needed longer than the wait was cancelled by its exit tail rather than waited for.
  The set is honest about what it caught (Escape is in the timeline), but it is not
  a latency measurement.
- **One terminal geometry.** Every session is 50x160. Behaviour at narrow widths,
  which is where a TUI's layout changes most, is not covered.

## Blocking prerequisite for W2: volatile-span masking

**These frames do not carry the volatile-span masking §7.1 requires, and no golden set
may be built from them until a capture does.** Everything measured in this report —
526 frames, 436 distinct screens, the frame-rate numbers, the "what was on screen"
claims — describes an unmasked artefact. Masking is not a filter that can be applied
to it afterwards: a frame records which cells it drew, not which of those cells the
application re-drew for no reason, so the spinner glyphs, the turn timer and the
streaming cursor in these frames are indistinguishable from content.

What is missing, and in what order it has to be fixed:

1. **The recorder has no event stream.** `crates/capture/src/screen.rs` builds every
   frame with `event_between: true` — "assume an event may explain this change" —
   because the application's own event stream is not wired into the recording path.
   That is §7.2's work. Until it is wired, passing `false` would label every change
   the application made of its own accord as noise, which is worse than no masking.
2. **No frame names the events it drew.** `Frame::acp_event_range` exists (added by
   the final review) and is `None` in all 526 frames of this set, which is the honest
   value while no stream is wired. Label alignment (§7.2) reads it.
3. **The capture has to be re-taken.** With spans recorded, the frame count, the
   distinct-screen count and the gap statistics in this report all change — a spinner
   tick that is masked is no longer a distinct screen — so `docs/reports/w1-index.json`
   describes this run only.
4. **Then, and not before, a golden set.** A golden set drawn from these frames would
   teach that a spinner is content.

## Changes to the session format after this capture

The 35 sessions here were written before `SessionRecord` carried `child_env` and
`cwd`, and before `Frame` carried `acp_event_range`. All three default on read (empty,
`None`, `None`), so every session in this set still reads back — verified with
`read_frames` over all 35 directories after the fields were added: `sessions read:
35/35 dirs, frames: 526`. Newer sessions record the merged environment the child
actually saw and the directory it ran in, which is what a reader needs to reproduce a
screen: this set records only the driver's two defaults (`TERM`, `COLORTERM`) in
`env` and nothing at all about the environment it inherited or the directory the
application ran in.
